# 0032: Faster client reads: bulk reads, delta sync, persisted queries over GET

- Status: accepted (owner's decision, 2026/11/26)
- Date: 2026/11/26

## Context
The extension and the cyex deck read one set, one channel and one emote at a time, then poll the whole set again whenever its `ETag` changes. A deck watching 30 channels makes 60 requests to start and rereads a 1.000-emote set to learn that one emote was renamed. GraphQL answers never cache at the edge (ADR 0008), so the website's public reads (the announcement banner on every page, the public limits) all reach the API. The API review (2026-11-26, future items 6 to 9) asked for bulk reads, delta sync, cacheable GraphQL reads, and a look at the 100-chatter personal-set cap. Everything here is additive: no field, answer or limit changes for existing clients.

## Decision
**Bulk reads.**
- GraphQL `emotes(ids: [ID!]!)`, `sets(ids: [ID!]!)` and `channels(platform, ids: [String!]!)`; REST `POST /v1/sets/lookup` (`{ ids }`) and `POST /v1/channels/lookup` (`{ platform, ids }`), shaped like `POST /v1/personal-sets/lookup`.
- The answer keeps the order asked, lists each item once, and leaves out what is unknown or hidden. Visibility is the single read's rule (`emote`, `set`, `channel`), checked for all IDs at once; REST answers as signed out (approved emotes only), like the other chat-client reads.
- Caps: 100 emotes, 100 channels, **25 sets**. A set holds up to 1.000 emotes (staff sets up to 1.000.000), so 25 sets is already up to 25.000 members in one answer, about what a client watching 25 channels needs at once. Over the cap is `too_many` (400).
- The SQL is batched: a fixed handful of statements however many IDs (`ANY($1)` reads for the rows, their owners, tags, counts, and one `editors::set_access` query for what a signed-in viewer may edit). A test counts the statements for 2 and for 20 IDs and wants the same number. The one exception: a pending emote of another account costs one query per such owner (to check an account editor grant), and a private set no channel shows costs one permission check per request, both rare.
- Rate limits: a REST lookup counts as one read (`reads`, 1.200 a minute per IP), as the personal-set lookup does; the caps bound the work. In GraphQL the complexity limit (1.000) prices them: `sets` costs what that many `set` lookups would (`ids × (10 + child)`), `emotes` and `channels` cost one lookup per 10 IDs (`5 + ⌈ids/10⌉ × (10 + child)`), since they are cheap rows read in one statement.
- `editors::set_access` replaces the per-set loop in `views::editable` (three queries per set for a signed-in viewer) for every set read, not only the bulk ones. Same rule, one query.

**Delta sync for sets.**
- `emote_sets.version` (bigint, from 0) goes up for every statement that changes what the set shows: a member added, removed, renamed or its zero-width flag changed, the set renamed, an emote in it changed (name, flags, state, file, owner, deleted), or its file got its variants or failed. Capacity, visibility and editors don't bump it.
- **Triggers, not explicit bumps.** Statement-level `AFTER` triggers with transition tables on `emote_set_members` (one bump per set per statement, so cloning 1.000 emotes is one version), a `BEFORE/AFTER UPDATE OF name` pair on `emote_sets`, and row-level triggers with column lists on `emotes` and `files` (so the nightly popularity and channel-count refreshes never fire them). Every write path, including ones added later (moderation, account erasure, transfers), is covered in the same transaction, which explicit bumps can't promise. Each bump locks the sets it touches in ID order, so two statements never deadlock on them; a set row's lock also orders its versions by commit.
- Each bump writes the touched members to `emote_set_changes (set_id, version, emote_id, kind)`. The worker's clean-up keeps 7 days and at most the newest 1.000 versions per set, and raises `emote_sets.change_floor` to the newest version it pruned.
- `version` is on `EmoteSet` (REST and GraphQL). `GET /v1/sets/{id}?since=<version>` and GraphQL `setChanges(id, since)` answer `SetChanges`: `version`, `name`, `added`, `renamed`, `updated` (whole `SetEmote`s, applied as upserts by emote ID) and `removedIds` (deletes). They are computed from the log and the set as it is now, read in one repeatable-read snapshot: every member touched since `since` is answered as it is now (present: an upsert; gone or not visible to the caller: removed). Applying a delta to any copy at or after `since` gives the current set, whoever asks (the public view, an editor's view with pending emotes).
- **Full resync**: `since` below `change_floor`, above `version`, or more than 2.000 change rows behind answers `full: true` with the whole set in `set`. `ETag` and `If-None-Match` work on both answers as on the set.
- What a delta doesn't follow: an emote's `channelCount`, its owner's display name and its tags (none change how chat shows it). A full read has them.

**Cacheable GraphQL reads: persisted queries over GET.**
- Automatic Persisted Queries, Apollo's protocol: `extensions.persistedQuery = { version: 1, sha256Hash }`. A hash alone runs the stored text, or answers `PersistedQueryNotFound` (code `persisted_query_not_found`); the text with its hash stores it (`persisted_query_mismatch` when they differ, `bad_persisted_query` when malformed). The store is per instance, in memory, at most 5.000 queries of up to 32 KB, oldest out first; a miss elsewhere costs the client one round trip. It works over POST too.
- Our extension puts the text back into the request before parsing, rather than handing async-graphql a parsed document (its built-in extension does that): the Snowflake translation reads ID literals from the text (ADR 0027), and every other rule then runs exactly as for a plain request.
- `GET /v1/gql?query=…&variables=…&operationName=…&extensions=…` runs **queries only**. A document with a mutation or subscription anywhere in it is refused (`post_required`, 405, `Allow: POST`), so a link or an image tag can never change anything. Without `query` or `extensions`, `GET` still opens GraphiQL.
- **CSRF:** `GET` never reads the session cookie: a cross-site `GET` from a signed-in browser runs signed out, so it can't even spend that account's rate limits or reach its data (`exportMyData` is a query). A Bearer token (apps, console tokens) is read; browsers never send one on their own. Mutations stay POST-only, under the existing `Origin` check.
- **Caching:** a signed-out answer without errors is `Cache-Control: public, max-age=30, stale-while-revalidate=60` with a strong `ETag` (and `304` for `If-None-Match`), as the REST reads. A Bearer answer is `private, no-cache`; an answer with errors is `no-store`. Every answer has `Vary: Authorization` (and `Origin`, from CORS). `GET /v1/gql` counts under the GraphQL limit (300 a minute per IP), and a Bearer caller under their account's, as POST does. Other origins may call it (`Access-Control-Allow-Origin: *`, no credentials), like the REST reads.
- **Website:** `gqlPublic` sends a query as `GET` with its hash, without credentials, and falls back to sending the text once on a miss; used for the reads that are the same for everyone (the announcement banner, the public limits). Everything signed-in, and every mutation, stays `gql` over POST.

**The 100-chatter personal-set lookup cap stays** (review item 9). A personal set holds at most 5 emotes, so 100 chatters is at most 500 emotes, an answer the size of half a channel set; a chat client sees new chatters a few at a time and batches them per 100 already. Streaming (NDJSON or chunked JSON) would take one long request instead of a few short ones, couldn't be cached or retried in parts, and would need a new client parser in the extension and the deck for no fewer queries (the lookup is one statement whatever the count). Raising the cap only makes one answer bigger. Not done; if a client shows it needs more, the same batched read can take 250 without other changes.

## Alternatives
- **Explicit version bumps in each write path:** visible in review, but every future write path must remember them, and the moderation, erasure and transcode paths write members and emotes from several crates. Triggers can't be forgotten.
- **A global sequence as the version:** cheaper (no set row lock), but versions would skip and a client couldn't tell a gap from a lost change; per-set counters under the set's lock are dense and ordered.
- **Deltas from the event outbox:** the outbox holds 48 h and is per event, not per set; a log per set kept a week is a clear contract and prunes on its own terms.
- **async-graphql's `ApolloPersistedQueries`:** stores a parsed document and empties the text, which skips the Snowflake ID translation for literals; a small extension of our own keeps every request on one path.
- **A fixed allow-list of persisted queries:** safer against store flooding but needs a build step for every client; the bounded store and the existing limits make the automatic protocol cheap enough.

## Consequences
- Clients start with a few calls instead of one per channel and set, and keep a set current with small answers; public GraphQL reads can be cached by Cloudflare and browsers.
- Every write to set members now also writes a change row and updates the set row. Bulk writes cost one row per member touched, in the same transaction.
- The set row is locked by every change to its members; edits to one set were already serialised by `lock_set`, so nothing new waits.
- `GET /v1/gql` is now an API endpoint, not only GraphiQL: proxies must not cache it beyond its `Cache-Control`.
