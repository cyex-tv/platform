# 0016: Cosmetics shop and redeem codes

- Status: accepted
- Date: 2026/11/17

## Context
ADR 0015 built cyex.tv's chat cosmetics with entitlements whose source is `grant`, `purchase` or `event`, and only `grant` written. The owner wants the rest: a shop where people buy badges and paints (for themselves or as a gift), and redeem codes for giveaways, like 7TV's Store and Redeem pages (studied from what 7TV shows publicly; no code taken, AGENTS.md).

D17 and ADR 0011 keep cyex.tv apart from cyex.app. cyex.app already sells cyex deck supporter badges through its own Paddle account in cyex-api; cyex.tv must not touch that setup.

## Decision
- **Payment provider: Paddle Billing**, with cyex.tv's **own** Paddle account, products, prices, API key, client token and webhook secret, set up by the owner. Nothing is shared with cyex.app's Paddle setup. Paddle is the merchant of record, so it handles VAT and the buyer's payment details; **no card data ever reaches cyex.tv**.
- **Settings (env, all optional):** `CYEX_TV_PADDLE_ENV` (`sandbox`, the default, or `production`), `CYEX_TV_PADDLE_API_KEY`, `CYEX_TV_PADDLE_CLIENT_TOKEN`, `CYEX_TV_PADDLE_WEBHOOK_SECRET`. A key or client token of the other environment (`pdl_live_`/`live_` in sandbox, `pdl_sdbx_`/`test_` in production) stops the api at start. Without the API key the shop still lists items, and `startCheckout` answers `checkout_unavailable`; without the secret the webhook answers 503. Tests and CI use a fake Paddle server only; never real money.
- **Items:** staff with `shop.manage` make items: name (1 to 64), description (up to 500), a bundle of 1 to 10 badges and paints, a shown price in cents (0 to 100000) and currency (ISO 4217, default `EUR`), the Paddle price ID (`pri_…`), an optional sale window (`activeFrom`/`activeTo`), an optional stock limit, a visible flag and a sort order. Deleting an item hides it for good; its orders stay. Deleting a cosmetic takes it out of every item.
- **Checkout:** `startCheckout(itemId, recipient?)` checks the item is on sale (visible, in its window, has cosmetics, in stock), finds the gift recipient by Twitch or Kick login (a live account), and refuses when the recipient owns every cosmetic in it already (`already_owned`; an owner can still gift it). Under a lock on the item row it counts paid orders plus pending ones of the last hour against the stock (`sold_out`), makes a pending order at the item's current price, then creates a Paddle transaction (`POST /transactions`, one of the price, `custom_data.cyex_tv_order_id`). It answers the transaction ID, Paddle's hosted checkout link when the account has one, the client token and the environment; the website opens Paddle.js's overlay with the transaction. A Paddle failure marks the order failed (`payment_provider_error`).
- **Fulfilment only from Paddle's signed webhook**, `POST /v1/shop/paddle/webhook`. The raw body is checked against `Paddle-Signature` (`ts=…;h1=…`, HMAC-SHA256 of `"<ts>:<body>"` with the secret, compared in constant time, any of several `h1` during secret rotation); a `ts` more than 5 minutes from now is refused (`stale_signature`). Each event's `event_id` is recorded in the same transaction as its effect, so a redelivered or replayed event does nothing. `transaction.completed` finds the order only by the transaction ID stored at checkout (never by `custom_data` alone: anyone can make a Paddle transaction with the public client token and tag it with any order; a `custom_data` order ID that disagrees is ignored too). Only a pending order is fulfilled, and only when the transaction is exactly what the checkout made: one item, the Paddle price snapshotted on the order, quantity 1, in the currency Paddle gave the transaction (the total isn't compared, since Paddle adds the buyer's tax by location); otherwise it is logged and audited as `shop.order_mismatch` and nothing is granted. A matching completion gives the recipient every cosmetic of the item they don't own yet as entitlements with source `purchase` and the order's ID, stores what Paddle says was paid, and marks it paid. `transaction.canceled` fails a pending order. An approved full `refund` or a `chargeback` adjustment (`adjustment.created`/`updated`) refunds a paid order; a partial refund is only audited (`shop.order_partial_refund`); an adjustment for an order still pending is answered 503 (not recorded), so Paddle delivers it again later. Other events are acknowledged and ignored.
- **Refunds:** staff with `shop.orders` refund paid orders (`refundOrder`, with a reason). When Paddle is set up, it first asks Paddle for a full refund (`POST /adjustments`, `action: refund`, `type: full`); if Paddle refuses, nothing changes (`refund_failed`). Then, like a refund from the webhook, it takes back exactly the entitlements the order made (by `order_id`); a selection of them is cleared by the existing foreign keys and publishes `user.cosmetics_updated`.
- **Orders:** refund reasons are staff notes, shown only to `shop.orders`. Buyer, recipient, item and its name at the time, status `pending` | `paid` | `refunded` | `failed`, the price at checkout, what Paddle says was paid, Paddle's transaction and adjustment IDs, times. `myOrders` (bought or received), `order(id)` (buyer, recipient or `shop.orders`), staff `orders` filtered by status, account and item.
- **Redeem codes:** staff with `codes.manage` make a batch: a name, a prefix (1 to 12 letters or digits), 1 to 1000 codes, uses per code (1 to 10000, default 1), an optional expiry, and what a code gives: a shop item's cosmetics (as they are when redeemed) and/or chosen badges and paints. Codes look like `PREFIX-XXXX-XXXX-XXXX-XXXX` (16 characters of Crockford's base32, 80 random bits). Only the sha256 of the normalized code (upper case, no spaces or dashes, O read as 0 and I/L as 1) is stored; the plain codes are in the answer to `createCodeBatch` and never again, and never in the audit log. Redeeming looks the hash up, compares in constant time, and refuses disabled (`code_disabled`), expired (`code_expired`), used up (`code_used_up`) and already used by this account (`already_redeemed`) codes, and codes that would give nothing new (`already_owned`, no use taken). Entitlements get a new source, **`code`** (an additive enum value; cleaner than reusing `event`), with the code's ID. Staff can disable a batch.
- **Guessing:** 30 redeem tries an hour per account; wrong codes lock an account out after 5 and an IP after 20 within 15 minutes, until those 15 minutes are over (`locked_out`, 429). In memory, like the other limits.
- **Permissions:** `shop.manage`, `shop.orders`, `codes.manage`, in `permissions::ALL` like the cosmetics ones (the owner holds all; admins get them through a role).
- **Audit:** `shop_item.created`/`updated`/`deleted`, `shop.order_paid`, `shop.order_failed` and webhook refunds (actor none, the system), `shop.order_refunded` (staff or the webhook, with `via`), `code_batch.created`/`disabled`, `code.redeemed` (the redeemer, target the batch).
- **Limits:** 30 checkouts an hour per account; staff shop and code writes count against the cosmetics writes limit (300 an hour). The webhook has no rate limit; it costs one HMAC before anything else.
- **Events:** purchases and codes change only what is owned, which is private (ADR 0015 sends nothing for grants either), so they send nothing. A refund that clears a selection sends `user.cosmetics_updated`. No new event type.
- **API (additive, ADR 0008):** types `ShopItem`, `ShopItemInput`, `Order`, `OrderStatus`, `OrderPage`, `Checkout`, `RecipientInput`, `CodeBatch`, `CodeBatchInput`, `CodeBatchPage`, `CreatedCodeBatch`, `RedeemResult`; `EntitlementSource` gains `CODE`; queries `shopItems`, `shopItem`, `myOrders`, `order`, `orders`, `codeBatches`; mutations `createShopItem`, `updateShopItem`, `deleteShopItem`, `startCheckout`, `refundOrder`, `redeemCode`, `createCodeBatch`, `disableCodeBatch`; REST `POST /v1/shop/paddle/webhook`.

## Consequences
- The owner sets up the Paddle account, products, prices, client token and webhook (`docs/setup/owner-steps.md`), and puts the price IDs on the items.
- A staff refund takes the cosmetics back before Paddle approves the refund; if Paddle later rejects it, staff grant them again by hand.
- Stock is held by a pending checkout for an hour; abandoned checkouts free it after that.
- Lockouts and limits reset when the api restarts and apply per instance (v1 runs one).
- Covered by Postgres tests in CI with a fake Paddle server (`apps/api/tests/shop_flow.rs`) and unit tests of the checks, the signature, the code format and the lockout.
